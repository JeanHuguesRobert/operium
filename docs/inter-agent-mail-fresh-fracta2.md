## Design update — multiple sovereign Cogentia Digital Twins (2026-11-10)

**New explicit Principal requirement:** John is only the first Cogentia Digital Twin instance; future independent twin instances each require an internal inter-agent email system. **Do not bind mailbox tenancy, routing identity, or authorization to `jhn`, the current Fracta2 machine, or `mail.fractavolta.com`.** See the canonical architecture [Federated Inter-Agent Mail](https://github.com/JeanHuguesRobert/cogentia/blob/main/research/federated_twin_interagent_mail.md).

Implementation must separate stable `twin_instance_id`, delegated `actor_id`, transport-specific mailbox alias, and the twin's trust perimeter. A single Stalwart deployment serving **multiple independent tenant mail systems** is the Principal's preferred architecture; John is only the first provisioned tenant. Stalwart Enterprise exposes Tenant objects, memberTenantId, tenant administrators, domain/account isolation and quotas. Stalwart Community can host multiple domains/accounts but does not provide documented Enterprise tenant isolation. Verify Enterprise entitlement before provisioning separately governed twins; separate Stalwart stores and federation remain fallback options when necessary, not the default; public MX and SMTP are **not prerequisites** for private federation. A Gmail bridge belongs only to the Principal-to-twin interface and must never become a shared credential or universal transport for other twins. COP must refuse any assumption that possession of an email address or private-network route implies delegation.

**Acceptance extension:** negative cross-tenant mailbox tests, authenticated inter-twin relay, delivery/processing receipt distinction, portable twin identity across mail stores, and demonstrated absence of external relaying. No operational authorization to install/open services is implied by this architectural update.

**Edition gate (2026-11-10, verified upstream):** `https://www.stalw.art/docs/auth/authorization/tenants/` and `https://stalw.art/docs/server/enterprise/` explicitly label real tenant objects/isolation **Enterprise-only**. The architectural target is one multi-tenant Stalwart installation with one tenant per Cogentia Digital Twin; multiple mailbox domains in Community are not equivalent. A successful bootstrap wizard does not establish an Enterprise licence or multi-tenant capability.

## Private-only scope, security proportionality (2026-11-10)

Principal clarifies that inter-agent mail **will not be Internet-visible**. Therefore do **not** configure public SMTP/IMAP/JMAP, public MX delivery, DKIM/SPF/DMARC or generic external spam/deliverability features as prerequisites. Within one trusted local runtime, use local/loopback transport and OS process isolation; additional message encryption or individual SMTP credential exchanges may be redundant. Between twin instances hosted by a single Stalwart daemon, nevertheless enforce distinct mailbox ownership, actor routing, and default-deny cross-tenant data access; the private network does not grant every user access to all mail. ## Canonical strict Twin confidentiality / no inter-Twin mail routing (2026-11-10)

**Principal rule:** « Ce qui se passe à l’intérieur d’un Twin reste à l’intérieur d’un Twin. » Stalwart mail is intra-Twin only, with isolation between Twins even if the underlying Stalwart deployment is multi-tenant. **There will be no Stalwart-to-Stalwart direct inter-Twin communication**, whether on the same host, across private networks or across Trust Perimeters. To communicate between Twins, the respective Principals exchange normal external email using their usual Gmail or other provider mailboxes. The Twin's provider-specific adapter may help its own Principal compose or read those messages within the Principal's authorization policy; the Principal controls what information crosses the boundary. JHN's explicit per-message authorization rule for external third-party sends still applies. Never present external email as an automatic COP mandate.

This **supersedes** earlier proposals in this dossier referring to private inter-Twin federation, relay, direct twin routing, or cross-Twin Stalwart delivery. For implementation, test negative *intra-server* cross-Twin leakage and verify external correspondence traverses only the Principals' regular provider accounts. No public Stalwart mail ports or MX are required.

## 2026-11-10 — Correct default TLS/ACME settings for private-only Stalwart

The Principal recalls possibly selecting an initial wizard option about TLS/certificates. **Do not confuse this with Caddy's independent HTTPS virtual hosts.** The wizard's persisted Stalwart settings need live verification through its **configured recovery-mode management UI** after running `enter-stalwart-configured-recovery-fracta2.sh --apply`; they have not yet been inspected as of this note. Upstream version 1.1 documented behavior:

- **Domain > TLS certificates:** each `Domain` has `certificateManagement`, either `Automatic` via an `AcmeProvider` (typically Let's Encrypt created by wizard) or `Manual`. For the private-only `mail.fractavolta.com` domain, select **Manual** if Automatic; this stops ACME issuance/renewal for that domain. Do not delete an ACME provider until all referencing domains have been checked. No public certificate is needed for the private transport.
- **Settings > Network > Listeners:** on normal startup, when there are **no** persisted `NetworkListener` objects, Stalwart v1.1 auto-generates wildcard listeners on SMTP :25, submissions :465, IMAPS :993, POP3S :995, ManageSieve :4190, HTTPS :443, and HTTP :8080. TLS settings are **per listener**: `useTls=false` disables STARTTLS; `implicitTls=false` gives cleartext HTTP, and for SMTP/IMAP without `useTls` false the default STARTTLS remains enabled. Create a **persistent explicit** HTTP listener e.g. `name=http-private`, `protocol=http`, `bind={"127.0.0.1:8080":true}`, `useTls=false`, `implicitTls=false`. For first local-agent SMTP consider e.g. `name=smtp-private`, `protocol=smtp`, `bind={"127.0.0.1:2525":true}`, `useTls=false`, `implicitTls=false`, subject to local Cogentia routing policy. In normal mode no Stalwart :443/465/993/25 public ports are wanted. Keep **at least one NetworkListener** or defaults regenerate. Do not claim any of these settings already applied. Listener edits take effect only after an explicit subsequent normal restart.
- **Security caveat of Stalwart UI:** upstream installation/security documentation notes that **WebUI sign-in in normal mode requires HTTPS/OAuth origin**, even though its HTTP API is accessible over private HTTP. Thus removing TLS from Stalwart's listeners may mean using the management API/CLI over loopback for routine administration or deliberately arranging a *private* TLS-terminating reverse proxy when interactive WebUI is needed. This is an application constraint, not a reason to expose Stalwart publicly or to force Caddy HTTPS as a prerequisite of the current recovery step. In **recovery mode**, WebUI explicitly accepts HTTP login, but the recovery listener binds `[::]:8080` and disables some abuse protections, so ensure guest firewall/OCI/private access continues to exclude unauthorised hosts.
